# 부동산 경공매 정보 플랫폼 개발 — 바이브 코딩 프롬프트 가이드
### (기획 → 설계 → 개발 → 배포)

> 행크옥션(hauction.co.kr) 벤치마킹: 법원경매·공매 물건 검색, 지도 기반 탐색, 시세분석,
> 커뮤니티(낙찰후기·칼럼·Q&A·판례), 회원제/멤버십 구조를 갖춘 부동산 투자 정보 플랫폼

---

## 0. 시작 전에 — 데이터/법적 이슈 정리

이 서비스의 핵심은 "코드"가 아니라 "데이터 소스"입니다. 개발 프롬프트를 쓰기 전에 아래를 먼저 결정하세요.

| 데이터 종류 | 확보 방법 | 비고 |
|---|---|---|
| 법원경매 물건정보 | ① 대법원 법원경매정보 사이트 이용약관 확인 후 자체 수집, 또는 ② 스피드옥션·지지옥션 등 유료 데이터 API 계약 | 대량 재배포는 약관 위반 소지 있음. MVP 단계에서는 유료 API 계약이 가장 안전·현실적 |
| 공매(온비드) | 공공데이터포털 온비드 Open API (공식 제공) | 무료, 안전 |
| 실거래가 시세 | 국토교통부 실거래가 공개시스템 Open API | 무료, 공식 |
| KB시세 | KB부동산 제휴 필요 | 스타트업 단계에선 생략 가능 |
| 지도 | 카카오맵/네이버맵/구글맵 API | 국내 서비스는 카카오맵 추천 |

바이브 코딩 프롬프트에는 "실제 크롤링 대상 사이트"를 명시하지 말고, **"확보된 API/데이터 계약을 전제로 한 연동 레이어"**를 만들도록 지시하는 것이 안전합니다.

## 1. 전체 로드맵

```
Phase 1  기획서(PRD) 작성
Phase 2  정보구조(IA) & 유저플로우 & 와이어프레임
Phase 2.5 UI/비주얼 아이덴티티 설계 (차세대 AI 인터페이스 톤)
Phase 3  기술 스택 & DB 스키마 설계
Phase 4  데이터 연동 레이어 (공공API 우선)
Phase 5  백엔드 API 개발 (NestJS)
Phase 6  Next.js 반응형 웹 프론트엔드 개발 (PC+모바일 통합, 유일한 클라이언트)
Phase 7  지도 기반 검색 & 시세분석 기능
Phase 7.5 자산관리 & AI 물건 추천 엔진
Phase 8  커뮤니티 (칼럼/후기/Q&A/판례) 기능
Phase 9  회원제 & 멤버십 결제
Phase 10 PWA 전환 (선택) — 홈 화면 추가, 푸시 알림, 오프라인 캐싱
Phase 11 테스트 & QA
Phase 12 배포 (웹 단일 배포)
```

> **최종 확정**: 별도 React Native 네이티브 앱 없이, **Next.js 반응형 웹 하나로 PC/모바일을 전부 대응**합니다.
> "모바일앱"에 대한 요구는 Phase 10(PWA — 홈 화면에 추가해서 앱처럼 쓰는 방식)으로 대체합니다.
> 나중에 앱스토어 등록이 정말 필요해지면 그때 이 웹을 Capacitor로 감싸거나 별도 네이티브 트랙을
> 추가하는 것을 추천드립니다 — 지금 단계에서 두 클라이언트를 병행 개발/유지보수하는 비용을
> 줄이기 위함입니다.

각 Phase마다 AI 코딩 도구(Claude Code, Cursor 등)에 그대로 붙여넣을 수 있는 프롬프트를 아래에 제공합니다.

## Phase 1. 기획서(PRD) 작성 프롬프트

```
너는 프롭테크 스타트업의 PM이다. 아래 조건으로 부동산 경공매 정보 플랫폼의
PRD(제품요구사항문서)를 작성해줘.

[서비스 개념]
- 서비스명: (가칭) OOO옥션
- 한 줄 정의: 법원경매·공매 물건 정보를 통합 검색하고, 지도 기반으로 탐색하며,
  시세분석과 투자자 커뮤니티를 제공하는 부동산 투자 정보 플랫폼
- 벤치마킹 대상 서비스의 핵심 기능(참고용, 카피 금지, 차별화 포인트 도출 목적):
  경매/공매 통합 검색, 지역별 지도 탐색, AI 시세분석, 낙찰후기 커뮤니티,
  전문가 칼럼, 경공매 Q&A, 법원판례 아카이브, 유료 멤버십/일일무료 이용권

[요구사항]
1. 타겟 유저 페르소나 3개 (초보 투자자, 경력 투자자, 전문 중개/컨설턴트)
2. MVP 범위와 이후 확장 로드맵(3단계: MVP → 성장기 → 확장기)을 구분
3. 핵심 기능 목록을 Must/Should/Could(MoSCoW)로 분류
4. 수익모델(멤버십 등급별 가격 정책, 광고, 제휴 강의) 초안
5. 경쟁사 대비 차별화 포인트 3가지 제안
6. 리스크 요인(데이터 라이선스, 법적 이슈, 사용자 신뢰) 명시
7. 성공지표(KPI) 정의 (가입자 수, 유료 전환율, 재방문율, 물건 클릭률 등)

결과는 마크다운 문서 형태로, 개발팀과 디자인팀이 바로 참고할 수 있도록 작성해줘.
```

## Phase 2. 정보구조(IA) & 유저플로우 프롬프트

```
위 PRD를 기반으로 아래를 작성해줘.

1. 전체 사이트맵(IA) — 메뉴 구조를 트리 형태로 표현
   (예: 홈 / 경매검색 / 공매검색 / 지도 / 커뮤니티(후기·칼럼·Q&A·판례) / 마이페이지 / 멤버십)
2. 핵심 유저 플로우 3가지를 단계별로 정리
   - 신규 방문자가 물건을 검색하고 상세페이지까지 도달하는 흐름
   - 무료 이용자가 유료 멤버십으로 전환하는 흐름
   - 회원이 낙찰 후기를 작성해 커뮤니티에 올리는 흐름
3. 각 플로우를 Mermaid 플로우차트 문법으로도 표현해줘.
4. 모바일 화면(좁은 뷰포트)과 데스크톱 화면에서 레이아웃/기능이 달라져야 하는 지점
   (예: 필터 패널 위치 - 데스크톱은 좌측 고정, 모바일은 하단 시트/모달, 네비게이션 방식 -
   데스크톱은 상단 헤더, 모바일은 하단 탭바)을 표로 정리해줘.
```

## Phase 2.5. UI/비주얼 아이덴티티 설계 프롬프트 — "차세대 AI 인터페이스" 톤

기존 경공매 사이트들은 대부분 표(테이블) 위주의 정보 나열형 UI라 신뢰감은 있지만 오래된 느낌을 줍니다.
이 서비스는 반대로 **"AI 비서가 데이터를 대신 분석해서 브리핑해주는" 느낌** — SF 영화 속 AI 비서(자비스류)의
톤을 참고하되, 실제 부동산 데이터 서비스에 맞게 절제된 형태로 구현합니다. 아래는 디자인 토큰 설계 →
검토 → 구현의 2단계 프로세스로 진행하는 프롬프트입니다.

### 2.5-1) 디자인 토큰/방향성 설계 프롬프트

```
너는 프롭테크 서비스 전담 UI/UX 디자인 리드다. 아래 브리프에 맞는 비주얼 아이덴티티를
설계해줘. 코드를 짜기 전에 먼저 "디자인 플랜"만 텍스트로 제시해줘.

[브리프]
- 서비스: 부동산 경공매 정보 + AI 자산관리/추천 플랫폼
- 톤: "차세대 AI 비서가 데이터를 분석해 브리핑해주는" 느낌.
  SF 영화의 AI 인터페이스(예: 자비스류)에서 받는 인상 — 정제된 다크 UI, 얇은 선으로 그려지는
  데이터 시각화, 정보가 스캔되듯 나타나는 느낌 — 을 참고하되, 과하게 사이버펑크스럽거나
  네온처럼 유치하게 가지 말고, "신뢰할 수 있는 금융/자산 데이터 서비스"의 절제됨을 유지할 것.
- 사용자는 실제 돈이 걸린 투자 결정을 내리는 사람들이므로, 화려함보다 "명료함 + 첨단감"의
  균형이 중요함.

[요청사항 - 디자인 플랜만 먼저]
1. 컬러: 베이스 팔레트를 4~6개 네임드 hex로 제시 (다크 베이스 + 데이터 강조 컬러 1~2개 조합 제안.
   단, 뻔한 '검은 배경 + 네온그린/시안' 조합을 그대로 쓰지 말고 이 브랜드만의 조합을 고민할 것)
2. 타이포그래피: 헤드라인용/본문용/데이터 라벨용(monospace 등 숫자 가독성 좋은 폰트) 역할 구분
3. 레이아웃 컨셉: 대시보드형 vs 브리핑카드형 등 후보 2~3개를 ASCII 와이어프레임으로 비교
4. 인터랙션 원칙: "AI가 분석 중" 느낌을 주는 로딩/전환 모션을 1곳에만 절제해서 적용하는 방안
   (과도한 파티클/글리치 효과 남발 금지)
5. 이 디자인이 흔한 "SaaS 대시보드 템플릿"이나 뻔한 "다크모드 크립토 대시보드"처럼 보이지
   않으려면 무엇을 다르게 해야 하는지 자체 비평(critique) 한 문단 포함

먼저 이 플랜만 제시하고, 내가 승인하면 그 다음에 컴포넌트 구현으로 넘어가자.
```

### 2.5-2) 컴포넌트 구현 프롬프트 (플랜 승인 후)

```
승인된 디자인 플랜을 기준으로 Tailwind CSS + shadcn/ui 기반 디자인 시스템을 구현해줘.

1. tailwind.config에 브랜드 컬러/폰트 토큰 등록
2. 공통 컴포넌트: GlassPanel(반투명 유리질감 패널), DataChip(수치 라벨),
   AIThinkingIndicator(분석 중 표시 — 은은한 스캔라인/펄스 애니메이션 1종),
   TrendSparkline(가격 추이 미니 그래프), StatusBadge(경매 상태 뱃지: 신건/유찰/낙찰 등)
3. 물건 상세페이지를 "AI 브리핑 카드" 형태로 재구성:
   - 상단: 핵심 지표(감정가/최저가/유찰횟수)를 카드형으로 요약
   - 중단: "AI 분석 요약" 섹션 - 시세 대비 저평가율, 리스크 요인을 자연어 브리핑 형태로 노출
   - 하단: 상세 데이터 테이블(원한다면 펼쳐보기)
4. 다크 테마를 기본값으로 하되, 라이트 테마 토글도 지원
5. 모션은 Framer Motion으로 구현하되 "reduce-motion" 접근성 설정을 존중하도록 처리
6. 반응형(모바일)에서는 카드가 세로로 쌓이며, 데이터 밀도를 낮춰 재구성

실제 화면 스크린샷을 찍어서 브리프와 비교 검토한 뒤, 과하게 화려한 부분이 있으면
한 가지씩 덜어내는 방식으로 다듬어줘 ("장식 하나를 빼는" 원칙 적용).
```

## Phase 3. 기술 스택 & DB 스키마 설계 프롬프트

```
아래 조건에 맞는 기술 스택을 추천하고, ERD 수준의 DB 스키마를 설계해줘.

[제약조건]
- 1인/소규모 팀이 바이브 코딩으로 빠르게 MVP를 만들어야 함
- 프론트엔드: Next.js(React) + TypeScript + Tailwind CSS — 반응형 웹 하나로 PC/모바일을
  모두 대응 (별도 네이티브 앱 없음, 필요 시 추후 PWA로 보완 - Phase 10)
- 백엔드: NestJS + TypeORM(또는 Prisma)
- DB: PostgreSQL (PostGIS 확장 — 지도 좌표 검색 위해 필수)
- 인증: 이메일/소셜 로그인 + JWT
- 결제: 국내 PG(토스페이먼츠 또는 아임포트) 연동 전제
- 배포: Vercel(프론트) + AWS/Railway/Render(백엔드) + 관리형 PostgreSQL(RDS/Supabase)

[요청사항]
1. 스택 선택 이유를 3줄 이내로 요약
2. 핵심 테이블 스키마 설계 (최소 아래 엔티티 포함)
   - users (회원, 등급/멤버십 상태 포함)
   - auction_items (경매 물건: 사건번호, 소재지, 좌표, 감정가, 최저가, 유찰횟수, 매각기일, 물건종류, 상태 등)
   - public_auction_items (공매 물건, 온비드 연동 필드 포함)
   - price_analysis (시세분석 결과: 물건 참조, 예상 시세, 산출 근거 데이터 소스)
   - bookmarks (관심물건)
   - community_posts (칼럼/후기/Q&A 공용 테이블, post_type 컬럼으로 구분)
   - comments
   - memberships (요금제, 결제이력)
   - regions (행정구역 코드 테이블 — 지역별 필터용)
   - user_assets, user_profile_finance, policy_rules, recommendation_logs
     (자산관리/AI추천 기능용 — 상세 스키마는 Phase 7.5에서 별도로 다룸, 여기서는 테이블명과
     users/auction_items와의 관계만 우선 잡아줘)
3. 각 테이블의 주요 인덱스와 PostGIS 좌표 인덱스(GiST) 설계 포함
4. ERD를 Mermaid erDiagram 문법으로 표현
```

## Phase 4. 데이터 연동 레이어 프롬프트

```
Node.js/NestJS 기준으로, 아래 외부 데이터 소스를 주기적으로 수집해
내부 DB(auction_items, public_auction_items)에 동기화하는 배치 모듈을 설계/구현해줘.

[데이터 소스]
1. 온비드(공매) 공공데이터포털 Open API — 인증키는 환경변수(ONBID_API_KEY)로 관리
2. 국토교통부 실거래가 Open API — 인증키는 환경변수(MOLIT_API_KEY)로 관리
3. 법원경매 물건정보 — (자체 계약한 유료 데이터 제공사의 API 스펙을 내가 별도로 제공할 예정이니,
```

## Phase 7.5. 자산관리 & AI 물건 추천 엔진 프롬프트

이 기능은 "사용자의 보유 주택 수·자산가액 + 최신 부동산 정책(세제·대출·규제지역 지정 등)을
결합해 적합한 경공매 물건을 AI가 추천"하는, 이 서비스의 핵심 차별화 포인트입니다.
다만 **세금/대출 한도 계산은 사실상 세무·금융 자문 영역**이라, 정확한 수치를 단정적으로
제시하기보다 "참고용 시뮬레이션 + 전문가 상담 권유" 형태로 설계하는 것이 안전합니다.

### 7.5-1) 데이터 모델 & 정책 데이터 연동 프롬프트

```
아래 기능을 위한 DB 스키마와 데이터 연동 구조를 설계해줘.

[신규 테이블]
- user_assets: 사용자 보유 부동산 정보 (주소, 보유형태(주택/입주권/상가 등), 공시가격 또는
  사용자 입력 추정가, 취득일, 대출잔액)
- user_profile_finance: 총자산, 가용 투자금, 대출 한도 관련 사용자 입력값(연소득, 기존 대출 등)
- policy_rules: 정책 규칙 테이블 (규제지역 여부, 취득세율 구간, LTV/DTI/DSR 한도,
  다주택자 중과 여부 등을 "효력 시작일자" 포함해서 버전 관리 - 정책은 자주 바뀌므로
  이력 관리가 필수)
- recommendation_logs: AI 추천 결과와 근거를 저장 (재현성/설명가능성 확보용)

[정책 데이터 소스]
- 국토교통부/행정안전부 고시 자료를 운영자가 주기적으로 policy_rules 테이블에 수동 또는
  반자동으로 업데이트하는 관리자 어드민 화면을 함께 설계해줘 (정책은 자동 크롤링보다
  운영자 검증 후 반영하는 것이 안전함).
- 정책 규칙에는 반드시 "기준일자"와 "출처(고시번호/공고링크)"를 함께 저장해 나중에
  근거를 추적할 수 있게 해줘.
```

### 7.5-2) 추천 로직 & API 프롬프트

```
아래 로직으로 "맞춤 물건 추천" 기능을 구현해줘.

[입력]
- 사용자의 보유 주택 수, 총자산/가용 투자금, 거주 희망 지역 or 투자 목적(실거주/투자/단타)

[처리 로직 - 규칙 기반 필터 + 스코어링, 블랙박스 예측모델 지양]
1. 1차 필터: 사용자의 가용 투자금 + 예상 대출한도(LTV 등, policy_rules 기준)로
   입찰 가능한 최저가 범위의 물건만 후보로 추림
2. 2차 필터: 사용자의 보유 주택 수에 따라 달라지는 취득세 중과 여부, 규제지역 여부를
   반영해 실질 취득 비용을 재계산
3. 스코어링: (감정가 대비 저평가율) + (관심지역 매칭) + (특수조건 리스크 낮음) 등을
   가중치 기반으로 점수화해 상위 N개 추천
4. 각 추천 물건에는 반드시 "왜 추천되었는지"(저평가율 X%, 예상 취득세 Y원, 대출한도 내 여부 등)
   근거를 함께 반환

[API]
POST /api/recommendations - 사용자 자산 프로필 기반 추천 물건 목록 반환
GET  /api/recommendations/:id/explanation - 특정 추천의 산출 근거 상세

[중요 - 반드시 반영]
- 응답에는 항상 "이 추천은 참고용 시뮬레이션이며, 실제 세금/대출 조건은 세무사·금융기관
  상담을 통해 확인해야 한다"는 disclaimer 필드를 포함해줘.
- 정책 데이터 기준일자가 오래된 경우(예: 90일 이상) 화면에 "정책 정보 갱신 필요" 경고를 표시.
- 확정적인 표현("무조건 이득", "OO% 수익 보장") 대신 "예상", "추정", "시뮬레이션 기준"
  같은 표현을 카피에 사용하도록 프론트엔드 문구 가이드도 함께 만들어줘.
```

```
/mypage/assets 페이지를 아래와 같이 구현해줘. (Phase 2.5의 디자인 토큰 사용)
```

## Phase 10. PWA 전환 프롬프트 (선택)

> 별도 네이티브 앱 없이 반응형 웹 하나로 가기로 했으므로, "앱 같은 느낌"을 보완하기 위해
> PWA(Progressive Web App)로 전환하는 단계입니다. 홈 화면 추가, 오프라인 캐싱, 푸시 알림까지
> 네이티브 앱 없이 상당 부분 구현할 수 있습니다.

```
Phase 6에서 만든 Next.js 앱을 PWA로 전환해줘.

1. next-pwa(또는 Next.js 공식 PWA 설정)로 manifest.json, 서비스워커 설정
   - 오프라인 시 최근 조회한 물건 목록을 캐시에서 보여주기
   - 정적 자산(이미지, 폰트) 캐싱 전략 설정

3. 웹푸시 알림 연동 (Web Push API + 백엔드 NestJS에서 발송 트리거)

   - 관심물건 매각기일 D-3/D-1 알림
   - 나에게 영향 있는 정책 변경 알림 (Phase 7.5 연동)
4. 앱 아이콘/스플래시 이미지 세트 준비 (iOS/Android 홈 화면 아이콘 규격 포함)

이 단계를 진행해도 여전히 URL 하나로 접근하는 웹앱이며, 앱스토어/플레이스토어 등록은
포함하지 않는다는 점을 문서에 명시해줘 (필요 시 이후 별도로 논의).
```

## 2. 바이브 코딩을 잘하기 위한 팁

1. **한 번에 다 시키지 말고 Phase 단위로 쪼개서 진행** — 위 순서대로 한 Phase씩 완료 후 코드 리뷰하고 다음으로 넘어가세요.
2. **매 Phase 시작 전에 이전 산출물(PRD, DB 스키마 등)을 컨텍스트로 다시 붙여넣기** — AI 코딩 도구는 세션이 길어지면 앞 맥락을 잊는 경우가 있습니다.
3. **API 키/시크릿은 절대 프롬프트에 실제 값으로 넣지 말 것** — `.env.example`만 요청하세요.
4. **데이터 라이선스 이슈는 코드보다 먼저 해결** — 법원경매 원천 데이터 확보 계약이 안 되어 있으면, MVP는 온비드 공매 데이터만으로 먼저 검증하는 것도 방법입니다.
5. **투자 관련 콘텐츠(후기/칼럼)에는 면책 문구를 기본 템플릿에 포함**하도록 매 프롬프트에 넣어두면 나중에 법무 검토가 수월합니다.
6. **AI 추천/자산관리 기능은 "설명 가능한 규칙 기반 로직"으로 시작하세요** — 세금·대출 관련 수치를 블랙박스 모델로 예측하면 나중에 오류 원인 추적이 어렵고, 사용자 신뢰도 떨어집니다. 정책 데이터는 운영자 검증 후 반영하는 어드민 프로세스를 꼭 함께 만드세요.
7. **UI를 "첨단감" 있게 만들되 매 화면마다 새로운 모션/효과를 넣지 마세요** — Phase 2.5에서 정한 "AI 브리핑" 톤 하나를 전체 서비스에 일관되게 적용하는 것이 오히려 더 고급스럽게 느껴집니다.
